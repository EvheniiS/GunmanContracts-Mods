# Agent guide for Gunman Contracts Mods

This is a collection of MelonLoader mods for Gunman Contracts – Stand Alone (Unity 6, IL2CPP, HurricaneVR). Use this file as the starting point for work in the repository.

## Where to look

- [README.md](README.md) is the public mod index and covers installation, build basics, dependencies, and the repository layout.
- [GAME_KNOWLEDGE.md](GAME_KNOWLEDGE.md) is how the game works (organised by topic: hooks, mechanisms, pitfalls, sound, flat mode); offsets are from game 0.3.1.x, so re-check them against the current build. [HISTORY.md](HISTORY.md) is a per-mod changelog, [ROADMAP.md](ROADMAP.md) open work and parked ideas, [GAME_UPDATES.md](GAME_UPDATES.md) the log of game updates. Check current source and the relevant mod's README before treating a historical note as current behavior.
- Each mod has its own directory and `.csproj`. Read that directory's README, testing notes, or roadmap when the task concerns that mod.
- [BlenderRefs/AGENTS.md](BlenderRefs/AGENTS.md) contains additional instructions for work in `BlenderRefs/`.

## Project boundaries

- Keep each mod's implementation in its own project. `Daredevil/` is the single package for Billy Clubs and Radar Sense; the former standalone projects are legacy. Gloves, Throw Assist, and Mod Settings are separate dependencies. Check current project files and documentation before changing dependencies.
- `release/<Mod>/` contains shipped DLLs and Nexus page material. Do not update release artifacts, versions, tags, or public release claims merely because source code changed. Verify the intended release and testing status first.
- **DLL name changes:** If an update changes the installed DLL's filename, explicitly tell the user the old and new filenames and that the old DLL must be removed from the game's `Mods` folder. Ordinary updates to a DLL with the same filename need no file-removal notice.
- The game installation, generated IL2CPP interop assemblies, `UserData/MelonPreferences.cfg`, and local `GameDir.local.props` are machine-specific. Do not commit them. Deploy built mod DLLs as required below; change preferences only when the task calls for it, and while the game is closed.
- Preserve unrelated work. Check `git status` before editing; do not discard existing changes or switch branches with a dirty checkout.

## Build and verification

- Build the affected project, not every mod by default. A typical command is `dotnet build <Mod>/<Mod>.csproj -c Release -p:GameDir="<game installation>"`. Alternatively, use that mod's git-ignored `GameDir.local.props` as described in the root README.
- **Always deploy every newly built mod DLL into the game's `Mods` folder before completing the task**, unless the user explicitly asks for a build without deployment. This is standing authorization; do not wait for another deployment request. Resolve the game directory from the affected project's local configuration, preserve a backup of the installed DLL outside `Mods`, copy the new DLL, and verify the installed file matches the build. Report deployment failures explicitly. Deployment does not mean the running game has loaded the update; tell the user to restart when needed.
- The .NET SDK and interop assemblies generated by MelonLoader 0.7.x are required for game-facing builds. If the local game installation is unavailable, report that limitation instead of treating an unrun build as a pass.
- Run focused checks for the change. Several mods have `TESTING.md` files or test projects; use them when relevant. A successful build does not establish that VR behavior works: mark gameplay claims as unverified until tested in game.
- Mod Settings default-change tests (popup, Updated defaults page, reset notice): `Tools/DefaultsTest/Test-Defaults.ps1`, skill `defaults-test`.
- Sound questions (which clip a holster, pickup or hit plays; replacing an effect): run `SoundProbe/` first (off by default; steps in its README), then read the log. Do not guess clips from field names.
- For game behavior research, use `il2cpp_tools/` and document the observed evidence and game version. Avoid turning a hypothesis or an older test result into a confirmed current fact.

## Documentation

- Update the affected mod's README or testing notes when its behavior or test status changes. Test status is the `Tested: <version> (<date>)` line near the top of the mod's README (newest version the user actually played, `Tested: none` if never); set it only when the user says they played that version (skill `mod-status`). The root README's Status column is generated by `Tools/Sync-Readme.ps1` and refreshed only when `dev` goes into `main`; do not hand-edit it on `dev`.
- Record game-code findings in `GAME_KNOWLEDGE.md` (by topic, with the game version and whether it was checked, inferred or untested); put a version's one-line change in `HISTORY.md`; playtest results go in the mod's README (the `Tested:` line, set by the user's word); unfinished work and ideas go in `ROADMAP.md`. Do not append dated per-version diaries. Keep this agent guide short and durable.

## Nexus

- What is live on Nexus: run `pwsh -File Tools\Check-Nexus.ps1 [-Docs]` (skill `nexus-status`). Read-only; needs `NEXUS_API_KEY` in the git-ignored `.env`. Mod folder to Nexus id mapping: `Tools/nexus-mods.json`. Preparing a release (build, zip, page-text lint, changelog, upload sheet): skill `nexus-release` / `Tools/Pack-Release.ps1`; it never uploads, tags or merges. Pushing a new version of an existing mod file (zip, version, changelog) is `Tools/Update-Nexus.ps1`: dry run unless `-Apply`, and `-Apply` only after the user confirms that exact mod and version. New pages and all page text stay manual; `Tools/Copy-Description.ps1 -Mod <Mod>` copies the page text to the clipboard and opens the edit page. Uploading or editing a Nexus page is public and the user's call every time; the API cannot edit page descriptions (details in `.claude/skills/nexus-status/references/nexus-api.md`).
